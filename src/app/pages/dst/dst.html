DST & Offsets

A timezone is not an offset. A timezone is a rulebook that says which offset applies at a given moment in history.

The relationship is one zone to many offsets. New York has used -05:00 and -04:00 in the same year, and its rules for switching between them changed in 2007. So the sentence "New York's timezone is UTC-05:00" is not just imprecise — it is a category error. The honest version is: "New York is currently observing UTC-05:00, under the rules in force today."

Every value on this page is computed live from your runtime's own timezone database, so it reflects the rules your users' browsers will actually apply.

GMT is not UTC

GMT — Greenwich Mean Time

Clock time at the Royal Observatory in Greenwich, derived from the Earth's rotation. It was the world standard from 1925 until 1972. Its problem: the Earth's rotation is not perfectly steady, so the second itself drifts.

UTC — Coordinated Universal Time

Established in 1972 on top of International Atomic Time, measured by caesium atomic frequency. It is the accurate replacement, kept aligned to the Earth's rotation by occasional leap seconds.

In everyday code the difference is under a second and the two names get used interchangeably. Prefer UTC anyway — it is the one with a definition that does not move. Note that Intl reports offsets with a GMT prefix rather than UTC; that is a naming convention in the standard, not a claim about atomic time.

DST is not one hour, and not always in summer

Lord Howe Island shifts by only 30 minutes. Any code that assumes a DST transition is ±3600000 ms is wrong there.

Southern hemisphere zones are inverted — Sydney and Santiago are on DST in January. "Summer time" is not a month range.

Many zones have none at all. Tokyo, Kolkata, Phoenix — and Tehran, which abolished DST in 2022. Never assume a transition exists.

Why IANA Names Exist

Given all of the above, a timezone cannot be a rule — it has to be a database. That database is the IANA Time Zone Database, usually called tzdata. Its main reliability target is civil-time data from 1970 onward, but historical coverage varies and future rules can change. Your result also depends on the tzdb release bundled by the runtime.

Area/Location

America/New_York, Europe/Bucharest, Asia/Seoul. The location is a city, not a country — deliberately, because cities outlive states. Zones group regions whose offset and DST history has been uniformly applied, which is why Seoul and Tokyo are separate entries despite sharing an offset today.

Windows uses a different database

Windows uses its own identifiers and rule representation — "Eastern Standard Time" rather than America/New_York. Unicode CLDR maintains mappings between the systems. Browsers expose IANA identifiers through Intl, while native and .NET APIs may use Windows identifiers.

The spec passes the buck

ECMA-262 defines the DST adjustment as an implementation-dependent algorithm using the best available timezone information, with only a recommendation that engines use IANA. So the correctness of your date handling is, formally, a vendor's best effort — and stale tzdata in an old runtime is a real source of wrong answers.

THE BIG ONE

You cannot convert zones by adding an offset

@let trap = conversionTrap();

This is the mistake that motivates every timezone library ever written. The pattern looks reasonable: read the offset difference between two zones, shift the timestamp by it, and shift back when you are done. It works — right up until the user edits a date across a DST boundary, because the offset you captured is no longer the offset that applies.

Rules to Remember

  • ✓ Store instants, not wall-clock readings. An epoch number or an ISO string with an offset survives DST. A local timestamp does not.
  • ✓ Store the IANA zone name alongside it when the user's intent was a wall-clock time — "09:00 in Europe/Bucharest" for a recurring meeting. An offset alone cannot reproduce it next year.
  • ✓ Test on a DST boundary. Add 10 March and 3 November 2024 in America/New_York to your test fixtures. See the Switch Timezone tab for how.
  • ✗ Never cache an offset and reuse it for another date. It is a reading of the rules at one instant, not a property of the zone.
  • ✗ Never assume a DST shift is one hour, that it happens mid-year, or that it happens at all.
  • ✗ Never hand-roll zone conversion. The author of the article this page draws on tried, failed, and concluded the same thing: use a library, but understand what it is doing for you first.
