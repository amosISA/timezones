How Dates Work in JavaScript

new Date() returns an object. Its essential time value is a number of milliseconds since 1970-01-01T00:00:00Z (the Unix epoch), or NaN when invalid.

What does “midnight UTC” mean?

Midnight is 00:00:00, the start of a calendar day. UTC is the shared reference clock. So 1970-01-01T00:00:00Z means the start of 1 January 1970 on the UTC clock; Z means a zero UTC offset. At that same instant it was 01:00 in Madrid and 19:00 on the previous day in New York.

A Date does not store an IANA zone such as Europe/Madrid. The GMT+0200 shown in the console is produced when the runtime renders the stored instant using the host's timezone rules. Parsing and formatting are the two boundaries where that interpretation enters.

Every value on this page was computed live, in your browser, in {{ localTimezone() }}. Open this page from a machine in another zone and several of the numbers change — that is the entire lesson.

TRAP 2

Months count from zero

In the numeric constructor, January is 0 and December is 11. Inherited from Java's java.util.Date. Every other field — year, day, hour — is one-based. Only the month is not.

new Date(2024, 6, 15)

{{ zeroIndexedMonths().wrong }}

Reads like "June 15". It is July.

new Date(2024, 5, 15)

{{ zeroIndexedMonths().right }}

June actually needs a 5.

Do not fight it — the numeric constructor has one real advantage that makes it worth the annoyance: its values are unambiguously local. No parsing rules, no string format guessing. If you need UTC instead, wrap it: new Date(Date.UTC(2024, 5, 15)).

TRAP 3

Anything that is not ISO 8601 is a coin flip

The spec requires its Date Time String Format plus invariants for strings produced by toString() and toUTCString(). Other formats are implementation-defined — engines are free to guess, and they disagree. Below is what your engine did:

Do not read the "parsed" rows as permission. A string like "2024-06-15 12:00:00" — an ISO date-time with a space instead of T — is not valid ISO 8601. V8 accepts it anyway; other engines have historically returned Invalid Date. It works on your machine and fails on a user's. Never rely on it.

TRAP 4

Two identical Dates are not equal

a and b below hold the same instant. Equality operators compare object identity, so they are false — but relational operators coerce to a number, so those work. An inconsistency you simply have to memorise.

@for (row of equalityRows(); track row.expression) {
{{ row.expression }} {{ row.value }} {{ row.reliable ? '✓' : '✗' }}
}

Compare with getTime(), or coerce with a unary +a === +b. And note the second-order trap: two Dates being equal instants is not the same question as two Dates being the same calendar day — the latter needs a zone before it even means anything.

TRAP 5

Every setter mutates in place

Date is mutable, and setMonth and friends return a timestamp rather than a new Date. Assigning a Date to another variable copies the reference, so mutating through one name changes both.

This is the single biggest reason the ecosystem moved to immutable date libraries — and why the incoming Temporal API makes every object frozen. Until then: always copy before you set.

TRAP 6

Out-of-range values roll over silently

There is no 30th of February, so JavaScript quietly moves on rather than throwing. This is genuinely useful for arithmetic — and genuinely dangerous for validation, because a typo never surfaces as an error.

@for (row of rolloverDemo(); track row.expression) {
{{ row.expression }} → {{ row.result }}
}

Use it deliberately. "30 days from now" is just d.setDate(d.getDate() + 30). Month and year boundaries handle themselves.

Never use it as validation. User input of "February 31" becomes a valid March date. Range-check the numbers yourself before constructing.

TRAP 7

A day is not 86,400,000 milliseconds

Adding 24 hours of milliseconds adds exactly 24 hours of elapsed time. Adding a calendar day adds whatever that day happens to be. On a daylight-saving boundary those are different answers. Fixed to {{ dstArithmetic().zone }} below, where 2024-03-10 is only 23 hours long:

Start

{{ dstArithmetic().start }}

+ 86,400,000 ms  ·  elapsed time

{{ dstArithmetic().addedMilliseconds }}

The wall clock moved to 13:00. A "daily 12:00 reminder" just became 13:00.

+ 1 via setDate()  ·  calendar day

{{ dstArithmetic().addedCalendarDay }}

Wall clock preserved at 12:00. Only 23 hours of real time elapsed.

Neither is wrong — they answer different questions. "Remind me in 24 hours" wants the first. "Remind me tomorrow at noon" wants the second. Decide which one you mean before you write the arithmetic. Note also that setDate works in the runtime's local zone, so getting the calendar-day answer for some other zone needs a real timezone library.

Rules to Remember

  • ✓ Store and transmit instants in UTC — ISO 8601 with a Z or an explicit offset, or an integer epoch value.
  • ✓ Convert to local only at render time — the last possible moment before a human reads it.
  • ✓ Copy before you mutate — new Date(original) then call the setter.
  • ✗ Never parse a date-time string without an offset — the result depends on the machine that runs it.
  • ✗ Never use Date for a date-only value. A birthday is not an instant. "2024-06-15" is a calendar date and forcing it through a timestamp is what creates the off-by-one bug in Trap 1. Keep it a string, or use Temporal.PlainDate.
  • ✗ Never hand-roll formatting. Month-name arrays and zero-padding are solved problems — Intl.DateTimeFormat is built in, locale-aware and free.
