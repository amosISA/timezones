Libraries

Every library on this page exists because of the same two gaps in the language: Date cannot format to a pattern, and it cannot represent a zone other than the host's. Everything else they offer is a consequence of solving those two things.

Which means the honest first question is not "which library" but "do I need one at all". If you only render dates, Intl.DateTimeFormat already does that in every zone and every locale, for zero bytes.

The One Distinction Most Comparisons Miss

Before comparing APIs, compare where the timezone rules come from. This decides the download size, whether the data can go stale, and what happens on an old device. It matters more than syntax.

ENGINE-BACKED reads the runtime's ICU data

The library asks Intl for the offset and does arithmetic around it. It ships zero bytes of timezone data, and its rules are as current as the browser.

@for (library of engineBacked(); track library.name) { {{ library.name }} }

Trade-off: on an ancient engine with stale ICU data, you inherit that staleness.

BUNDLE-BACKED ships its own copy of tzdata

The library carries the IANA database in your JavaScript bundle. Consistent everywhere — and frozen at the version you installed.

@for (library of bundleBacked(); track library.name) { {{ library.name }} · {{ library.gzipKb }} kB } @js-joda/timezone · 38 kB

Trade-off: 100+ kB gzipped, and every government rule change needs a dependency bump and a redeploy.

The type split is the whole idea. Instant is a moment in time. PlainDate is a calendar date with no instant. PlainTime is a wall-clock reading. ZonedDateTime is an instant plus the zone it should be read in. Every bug in this app came from Date pretending all four were the same thing. Temporal makes those concepts different runtime types. TypeScript declarations and an explicit domain model can then catch many accidental mix-ups before production.

The Takeaway

  • → Reach for no library first. Intl covers display in any zone and locale. A large share of date dependencies are formatting wrappers around an API the browser already has.
  • → Prefer engine-backed over bundle-backed. Shipping 114 kB of timezone data that quietly expires is a worse deal than reading the browser's own copy.
  • → Write Temporal-shaped code now, whichever library you pick. Keep instants and calendar dates as separate types in your own model and the eventual migration is mechanical.
  • → No library saves you from not knowing this. The author of the article behind the DST page reached the same conclusion: use a library, but only after you understand what it is doing on your behalf. A tool you cannot debug is not an advantage.
