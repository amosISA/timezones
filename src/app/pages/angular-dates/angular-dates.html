Dates in Angular

Angular gives you two tools for formatting dates: the DatePipe in templates and formatDate() in TypeScript. They share the same engine, so the pipe belongs in templates and the function in code.

That engine is not Intl. @angular/common contains zero references to Intl.DateTimeFormat — Angular ships its own locale data, which is what registerLocaleData exists for. That is a defensible design with one very sharp consequence, which is the subject of this page.

DatePipe is Pure — a Clock Is Not

DatePipe is a pure pipe: it re-evaluates when its input reference changes. Mutating a Date in place therefore renders nothing, and under zoneless change detection a bare setInterval schedules nothing either.

A new Date each tick, so the reference changes; a signal write, so change detection is scheduled. Both problems, one line.

Server-Side Rendering

With SSR your component renders twice: once on the server, in the server's zone — almost always UTC — and once in the browser, in the user's zone.

Any template that formats a date using the ambient zone therefore produces different text in those two passes. The user sees the server's version, then a flicker as hydration replaces it. If the two renders disagree about the day, they see the wrong date first — and a test that only inspects the hydrated DOM passes.

The defence is to be explicit about the zone at every formatting site. If a value's rendering depends on Intl.DateTimeFormat().resolvedOptions().timeZone, it will differ between server and client by design. Either pass an explicit zone, or treat the value as client-only and render it after hydration.

And if the correct zone genuinely is the user's, the browser has to tell you. A request carries an IP address and an Accept-Language header; neither is a timezone. Standard request metadata does not carry a reliable timezone — capture or send it explicitly.

Configuring It Once

Default format and offset

The older DATE_PIPE_DEFAULT_TIMEZONE token is deprecated. Same limitation applies: that is an offset, not a zone.

Locale

Required because Angular uses its own data. An unregistered locale throws NG0701: Missing locale data; it does not silently fall back. Intl uses the runtime's locale data instead.

zone.js Is Not About Timezones

The naming here is genuinely cruel. zone.js is about execution contexts — it monkey-patches async APIs so Angular knows when to run change detection. It has no relationship to time, offsets, or the IANA database.

zone.js — the legacy change detection mechanism, patching async APIs

timezone — a region whose UTC offset varies by date

From Angular 21 onward, new apps are zoneless by default. There is no switch to find: internalCreateApplication installs the zoneless provider unconditionally and there is no zone.js in the dependency tree. If you are wondering what to configure to enable it, the answer is nothing — you already are.

This app still calls provideZonelessChangeDetection() explicitly, purely as documentation. An invisible framework default is a poor place to keep an architectural decision.
